# 简化多语言方案

## 当前情况

现在有两套多语言系统：

1. **`html-templates/`** - 用于 SEO meta 标签（静态 HTML 文件）
2. **`src/i18n/locales/`** - 用于页面内容翻译（React 组件通过 `t()` 函数）

## 用户需求

只保留 `html-templates/`，取消 `src/i18n/locales/` 的多语言化工作。

## 方案选择

### 方案 A：页面内容固定为英文（最简单）

**做法**：
- 移除所有 `useTranslation()` 和 `t()` 调用
- 页面内容硬编码为英文
- 只保留 `html-templates/` 用于 SEO

**优点**：
- ✅ 最简单，维护成本最低
- ✅ 只需要维护 HTML 模板文件

**缺点**：
- ❌ 页面内容只有英文，无法多语言化
- ❌ 用户体验不好（SEO 是中文，但页面内容是英文）

### 方案 B：页面内容也硬编码，但为每个语言创建独立组件（不推荐）

**做法**：
- 为每个语言创建独立的页面组件
- 每个组件硬编码对应语言的内容

**优点**：
- ✅ 页面内容可以多语言化

**缺点**：
- ❌ 代码重复严重
- ❌ 维护成本极高
- ❌ 不推荐

### 方案 C：保留 i18n，但简化（推荐）

**做法**：
- 保留 `src/i18n/locales/` 用于页面内容翻译
- 保留 `html-templates/` 用于 SEO meta 标签
- 但可以优化：让 HTML 模板从翻译文件读取内容（减少重复）

**优点**：
- ✅ 页面内容可以多语言化
- ✅ SEO 友好
- ✅ 维护成本适中

**缺点**：
- ⚠️ 仍然需要维护两套系统（但可以优化）

## 推荐方案

我理解您想要简化维护工作。建议采用**方案 C 的优化版本**：

1. **保留 `src/i18n/locales/`** - 作为唯一的翻译数据源
2. **保留 `html-templates/`** - 但让它们从翻译文件读取内容（通过构建脚本）
3. **移除重复** - HTML 模板不再手动维护，而是从翻译文件自动生成

这样：
- ✅ 只需要维护一套翻译文件（`src/i18n/locales/`）
- ✅ HTML 模板自动从翻译文件生成
- ✅ 页面内容仍然可以多语言化

## 如果坚持只保留 HTML 模板

如果您坚持只保留 `html-templates/`，那么：

1. **移除所有 i18n 相关代码**
2. **页面内容硬编码为英文**
3. **只通过 HTML 模板提供不同语言的 SEO meta 标签**

但这样会导致：
- 页面内容只有英文
- SEO 和页面内容不匹配（例如：中文 SEO，但页面是英文）
